Decision record 14: a queue for reminder jobs

Example Planner sends 2.4 million reminders a day, and the database table that holds them is too slow at the morning peak. We compared three ways to run the reminder jobs. We chose a managed message queue.

Decision record
  • Status: accepted
  • Decided 3 November 2026
  • Deciders: platform team, with the reminders team
  • Replaces decision record 9
  • Every name and number is invented

The decision

Accepted

We will move reminder jobs from the reminder_jobs table to a managed message queue, option B below. The move starts in the week of 16 November and ends before the holiday peak in December.

Option B is the only option that meets the delay target at twice today's peak and that the team can run without a new on-call skill. It costs $1,500 a month more than today. Option C is faster, but it needs a cluster that nobody on the team has run.

In one line Pay more each month, so that reminders are on time and the team keeps the work it knows.

Context

Each reminder is a job: "send this push message to this person at 09:00 in their time zone". A scheduler writes the jobs into the reminder_jobs table. Eight workers read the table every second, take the jobs that are due, and send them.

Most reminders are set for the full hour, so each time zone has a peak at 09:00. The largest peak today is 900 jobs a second.[1] At that rate the workers fight over the same rows, and some reminders arrive 14 seconds late. Customers notice a reminder that comes after the meeting started.

The number of reminders grew 70% this year. We expect twice today's peak by the end of 2027.

What the choice must meet

  • At twice today's peak, 99% of reminders leave within 5 seconds of their time.
  • A reminder is never lost. It may, rarely, be sent twice.
  • The platform team of five can run it, with the on-call skills it has today.
  • It is in production before 1 December 2026.

The three options

A. Keep the table, and tune it

Split the table by time zone, add an index on the due time, and let each worker lock a batch of rows with SKIP LOCKED. No new system. The database needs a larger machine.

B. A managed message queue

The scheduler puts each job on a queue that our cloud provider runs. Workers take jobs from the queue, and the queue hands each job to one worker. A job that fails comes back after a wait. We already use the same provider's queue for email.

C. An event log that we run

Run a cluster of three event log servers, with one partition for each group of time zones. Workers read their partitions in order. It is the fastest option, and it keeps every job for seven days, so we could replay a day of reminders.

How the options compare

We ran a load test of each option for two hours, at today's peak and at twice the peak, with copies of real reminders. Figure 1 shows the delay between a reminder's time and the moment a worker sent it, for options B and C: from the median (50%) to the 99th percentile (99%).[2]

Option A is not in Figure 1, because its delays do not fit the same scale. At today's peak the table took 0.8 seconds at the median and 14 seconds at the 99th percentile. At twice the peak it took 3 and 58 seconds. So the table fails the target already today. The queue and the event log both meet it at twice the peak.

How option B works

The scheduler keeps its job: it finds the reminders that are due in the next minute. In place of rows in a table, it puts one message for each reminder on the queue. The queue hands each message to one worker. The worker deletes the message when the push service accepts the reminder; if the push service fails, the message comes back after 60 seconds.

Each message carries a key made of the reminder's id and its time. A worker writes the key to the database after it sends the push, and skips a message whose key is already there. So a message that the queue hands out twice sends one push.

# One message on the queue
{
  "key": "rem_8f21c0:2026-11-16T09:00:00+01:00",
  "reminder_id": "rem_8f21c0",
  "due": "2026-11-16T08:00:00Z",
  "attempt": 1
}

Consequences

What gets better

  • Reminders leave on time at the peak, with room for two years of growth.
  • Workers no longer lock rows in the main database, so the database has less load at 09:00.
  • A failed push comes back by itself. The retry code in the worker goes away.

What gets worse

  • The cost goes up by $1,500 a month at twice the peak.
  • We depend more on one cloud provider. Moving away later means rewriting the scheduler and the workers.
  • A reminder can be sent twice when the key check fails. We accept this; a lost reminder is worse.
  • We cannot replay a day of reminders, as option C could. Today we cannot do that either.

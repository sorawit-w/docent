Do worked examples in API reference pages help developers finish tasks?

We asked 24 developers to do four tasks with an API they did not know, once with reference pages that held worked examples and once with pages that did not. With examples, they finished more tasks, finished them faster, and felt more sure of their code. The study is small, and the differences are uncertain in size.

The question

Reference pages list what an API offers: each call, its parameters and its answers. Many teams add a worked example to each call, a short piece of code that does one real task. Writing and testing these examples costs time, so teams ask whether they help.

Earlier studies found that developers look for examples first (Ortega and Lindqvist, 2019), and that tutorials with examples shorten the time to a first working call (Haddad and others, 2021). Fewer studies tested examples inside the reference pages themselves, for tasks beyond the first call.

We tested three expectations, written down before the study:

  1. With worked examples, developers finish more tasks.
  2. With worked examples, they finish tasks faster.
  3. With worked examples, they feel more sure that their code is right.
Registered plan The expectations, the measures and the analysis were registered before the first session (Example Lab, 2026). One change from the plan is named under Method.

What the results mean

All three expectations held. Worked examples helped most where the reference left out a step that the code needs, such as asking for the next page of a list. Where the description already said each step, as for signing a request, the examples helped little.

The effect on time agrees with the earlier tutorial study (Haddad and others, 2021), which found that examples cut the time to a first call by about a third. Our tasks were later steps, and the cut was about a quarter.

For a team that writes reference pages, the results suggest an order: write examples first for the calls whose use needs more than one step. Those are the calls where a description alone fails most often.

A quarter 2.3 minutes of 8.7 is 26%. The interval runs from 11% to 41%.

Method and limits

Method

Participants

24 developers took part, recruited through a developer mailing list. They had 2 to 15 years of work experience (median 6). None had used the test API before. Each received a $40 gift card.

Materials

We wrote reference pages for an invented payments API with 14 calls. Version A had a description, a parameter table and an answer table for each call. Version B was the same, with one worked example under each call: 8 to 20 lines of code that run as written.

Design and tasks

Each participant did four tasks: sign a request, read a long list page by page, check a webhook, and handle an error and try again. Each did two tasks with version A and two with version B. The order of the tasks and of the versions followed a Latin square, so each task was done equally often with each version and in each position.

Finished
The task's test passed within 15 minutes.
Time
Minutes from the start of the task to a passing test, for finished tasks only.
Confidence
The answer to "How sure are you that your code is correct?", from 1 (not at all) to 7 (completely), asked after each task.

Analysis

We compared the two versions within each participant. For each measure we report the difference between the versions and a 95% confidence interval from a bootstrap with 10,000 samples of participants.[2] We also give each difference as a standardized effect, d, so the three measures can be shown on one scale.

Change from the plan

The plan named a mixed model for the time measure. It did not converge with 24 participants, so we used the paired bootstrap for all three measures.

How d is worked out

For each participant, we took the difference between the two versions, then divided the mean of those differences by their standard deviation. For tasks finished, a participant's value is the share of their two tasks that they finished with each version.

# d for paired measures
d = mean(differences) / sd(differences)

What was left out

No participant and no task was left out. The time measure counts finished tasks only, so one participant, who finished no task without examples, is not in it.

How sure the result is

Each range is a 95% interval: with the same method on many samples, about 95 of 100 such intervals would hold the true value. These limits could make the result wrong:

  • A small sample. With 24 participants the intervals are wide. A study of about 80 would narrow the interval for tasks finished by half.
  • One API. The test API was small and invented. A large API with many ways to do one task may give a different result.
  • Our own examples. We wrote the examples for these tasks. Examples in real pages are often written for other tasks, so they may help less.
  • A lab session. Participants worked alone, in one session, with no search engine and no forum. At work, a developer who lacks an example can often find one.
  • Who took part. People on a developer mailing list may read documentation more than most.

Page layout for generated documents

How wide should the text of a Docent page be, where should it sit on a wide screen, and how should it print? This report collects the evidence, compares four layouts, and says what was decided.

Research report
  • Written 21 November 2026
  • 45 sources
  • Owner: Docent

Summary

Docent's text width is right. The 31rem column holds about 63 to 70 characters in a line. Readers prefer lines of about 45 to 76 characters, and no study found that this range hurts speed or comprehension.

The real problem was balance on wide screens. On a 1920px screen, the text and its notes sat 178px left of the middle. The fix is to center the text and its notes as a group, and let wide blocks grow to the right.

The kind of document and its readers should change the spacing, the width of code and tables, and navigation. They should not change the text width. Four profiles cover the common cases.

On paper, Docent should leave the paper size to the reader, set the text near 11pt, and keep a narrow text column.

How strong is it? The evidence for the text width is good. The evidence for where the text sits on a wide screen is weak: no study compares the options on modern screens.

What the evidence says

Each source has a kind. A study measured something. A standard is a specification, such as WCAG. A convention is practice or expert advice without its own data. Data is a usage or support statistic.

Screens and readers

Most desktop screens are wide enough for the text and its notes side by side. The layout needs about 844px, and every common desktop width is 1280px or more. Scaling makes the real window smaller: a 1920 screen at 125% gives a browser about 1408 to 1521px.

The public reads mostly on phones: 61% of visits to GOV.UK came from phones in 2025. For public documents, the single column is the main layout, not a fallback.

No recent data exists for developer documents, for on-call staff, or for managers. Screens wider than 1600px are probably at most 13% of page views on the general web.

An estimate The 13% is 0.385 desktop share times about 0.33 of screens that are 1920px or wider. No public data confirms it.

Line length

Studies of line length agree on what readers like, and disagree on speed. Longer lines were sometimes read faster, but readers rated them worse, and comprehension did not improve. Longer lines helped visual search, which weakly supports wider tables and code, not wider text. Most of these studies are old and small.

For readers with dyslexia, the evidence is about text size, not line length: sizes up to 18pt read better than 12pt. Guidance for older adults asks for 19px text. So the strongest concern is text size, not width. Because Docent sets its sizes in rem, a reader who sets a larger text size gets larger letters at the same line length.

Wide screens on other sites

Most documentation sites center a page of about 1440px, with navigation on the left and an "On this page" list on the right. Sites with no side columns center the text itself. The sites that keep one left edge for text and wide blocks always put something in the space on the right: Tufte CSS shifts the page, Observable shows a contents list, and GOV.UK shows related links.

No study

No study tests one left edge for text and code. No study compares centered and left-aligned text on modern wide screens. One eye-tracking study found that 80% of looks at 1920px fall on the left half.

Kinds of documents

Diataxis splits documents into study (tutorials and explanations) and work (how-to guides and reference). Reference is consulted, not read, and a how-to is a sequence of actions. Diataxis gives no layout numbers, so every layout below is an inference. Readers scan headings when the headings are clear, and that helps every kind more than any width does.

Fluid type and zoom

No study shows that text which grows with the screen helps reading. It has a known risk: the part of the size that follows the screen width does not grow with browser zoom, so text can fail WCAG 1.4.4. Docent keeps its body at 1rem, which has no such risk.

Four layouts for wide screens

The obvious choice would be to center everything, like most documentation sites. That is wrong for Docent if it keeps one left edge for every block, because a centered grid gives up that edge. The report compared four layouts. All positions are for a 1920px screen.

Signals in the content

  • Numbered steps, and sentences that start with a verb, point to Task.
  • An alert name, a severity, "rollback", and many commands point to a runbook, which is Task.
  • Many times of day, with "impact", "root cause" or "actions", point to Brief.
  • Many tables, option names, and little text point to Reference.
  • Long paragraphs, "how X works", diagrams and few commands point to Standard.
Not tested These signals are a synthesis of other tools and templates. No source tests them.

The wrong default

"The page has code, so use a dense, wide layout" is wrong. Tutorials and runbooks hold code too, and they need a plain single column.

Print

Paper size and text

The page sets no paper size, so the reader's choice wins. The page margin stays at 18mm, which works in all three browser engines. Print norms are 10 to 12pt, and today's 16px prints at exactly 12pt. So the body should be 11pt on paper.

A column as wide as the paper would hold 82 to 103 characters at 11pt, which is too long. So the text keeps a narrow column on paper, and only tables and code use the full width.

Margin notes

Option 1 keeps each note under its paragraph, which is safe. Option 2 keeps the notes beside the text, in a 112mm text column, an 8mm gap and a 50mm note column. That fits an A4 page.

Breaks, page numbers and closed sections

  • Keep a figure, a table and a code block on one page when they fit. Browsers treat these rules as hints.
  • Keep two lines of a paragraph together at a page break. Chrome and Safari do this; Firefox does not.
  • Page numbers work only in Chrome and Edge, so they are an extra. Other browsers print their own footer.
  • A closed section prints closed in browsers. The kit's page script opens it before printing.
  • Colors carry meaning only in status dots. The reader's setting can still drop backgrounds, so a code well needs a thin line.
